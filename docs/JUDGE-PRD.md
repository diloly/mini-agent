# mini-agent · 增量 PRD：LLM-as-judge 质量评测

> v1.0 · 许清楚（产品经理） · 下游：高见远（架构师）
> **增量 PRD**，只描述本次新增部分。输入：`docs/PROJECT-GUIDE.md`、主理人三轮澄清、用户原话「统计成案例，我们 trace 评测，为了优化 prompt 和后续可能会有的 RAG」「除了复制按钮，给他一个赞一个踩」。

## 0. 前提（已锁死）

| # | 前提 |
|---|---|
| P1 | **不用 ragas**：它是 Python 生态，而内置 Python 是 stripped 版只有标准库；judge 要和 UI/存储打通，走技能脚本（30s 超时、无回调）对不上。改为**自建轻量 judge** |
| P2 | judge 只走主进程（渲染层 CSP `connect-src 'none'`），复用现有 `chatStream`（忽略流式回调，不加非流式接口） |
| P3 | 不引新依赖（无 zod / 无评测框架 / 无 Python 桥） |
| P4 | **手动触发才跑**，绝不自动评 |
| P5 | **结果仅内部记录 + 设置页汇总**，对话界面不显示分数 |
| P6 | 产出物是**可复跑的 case**，不是一堆分数 |

## 1. 产品目标

**一句话**：把「一次问答 + 它的工具轨迹 + 它是用哪个 prompt/模型/工具集生成的」沉淀成可复跑的 case，用模型当裁判给分，让「换 prompt 到底变好没有」有数据可答。

| # | 目标 | 衡量方式 |
|---|---|---|
| G1 | **能沉淀**：点踩或点评测，该次回答即成为一条 case 落盘 | 点踩后 case 文件出现该条，含问题/回答/轨迹 |
| G2 | **能打分**：手动触发后输出 4 维分数 + 理由 | 设置页能看到该 case 的分数与理由 |
| G3 | **能对比**：同一问题在不同 prompt 版本下的分数可并列 | 改 prompt 重答同一问题并评测，两条 case 的 `promptVersion` 不同 |

## 2. 用户故事

| ID | 故事 |
|---|---|
| US-1 | 作为本地使用者，我想在不满意的回答下点「踩」，以便下次调 prompt 时知道该改哪里 |
| US-2 | 作为本地使用者，我想手动发起评测，以便不花没必要的 token 也能拿到分数 |
| US-3 | 作为调 prompt 的人，我想看到 case 记录了当时的 prompt 指纹与模型，以便区分是 prompt 变了还是模型变了 |
| US-4 | 作为长期使用者，我想在设置页看平均分、维度分布和踩的清单，以便判断最近改得变好还是变差 |
| US-5 | 作为以后要接 RAG 的人，我想把 case 导出成 JSONL，以便直接当评测集用 |

## 4. 数据模型草案（仅示意，不进 `shared/types.ts`）

```ts
type Verdict = 'up' | 'down';

/** 生成指纹：没有它就无法做 A/B，本设计最关键的一块 */
interface GenerationFingerprint {
  providerId: ProviderId;
  model: string;
  promptVersion: string;  // system 装配结果（工作区规则+技能清单+记忆）短哈希前 8 位
  toolSetHash: string;    // 当轮暴露的工具名排序后哈希：工具集变了分数不可比
  appVersion: string;
  turns?: number;
}

interface JudgeRun {
  runAt: number;
  judgeProviderId: ProviderId;
  judgeModel: string;
  rubricVersion: string;  // 评分标准自身版本，改维度定义时 +1
  scores?: { relevance: number; faithfulness: number; completeness: number; clarity: number }; // 1-5 整数
  overall?: number;       // 四维等权均值，保留 1 位
  reason?: string;        // 中文 ≤120 字，须指出最弱一维
  error?: string;
}

interface JudgeCase {
  id: string; conversationId: string; messageId: string; // messageId 为幂等键
  createdAt: number;
  question: string;
  questionHash: string;   // 同一问题的跨版本对比锚点
  answer: string;
  steps: ToolStep[];      // 工具轨迹快照
  finishReason?: FinishReason;
  verdict?: Verdict;
  generation: GenerationFingerprint;
  runs: JudgeRun[];       // 数组而非单值：换 judge 模型 / 换 rubric 可留历史
}
```

- `overall` **不加权**（等权），避免多出一堆可调参数。
- 平均分只取每条 case 最新一次成功 run，失败 run 不计入分母。
- 有 `errorCode` 或被中止的回答**不建 case**。

## 5. 评分维度与 1-5 分锚点（本土化 ragas）

judge 打不稳的根因是没锚点，每档必须给判定标准。

| 维度 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|
| **相关性**（是否答了用户问的那件事） | 答非所问 / 拒答 | 答了但漏主诉求 | 正面命中，无跑题铺垫 |
| **忠实度**（是否忠于工具结果与上下文，不编造） | 出现上下文中不存在的文件/数据/结论 | 大体有据，个别细节无来源 | 每个事实都能在工具结果或上下文里找到 |
| **完整性**（是否覆盖全部要点） | 只答一半 | 主要要点齐，次要缺失 | 要点齐且给出可执行步骤 |
| **表达质量**（结构、可读、无冗余） | 混乱 / 大段重复 | 可读但有冗余 | 结构清晰，结论先行 |

- 忠实度是**唯一带硬否决**的维度；但「无工具调用且无上下文」不等于 1 分，只按「是否有明显编造」判。
- ⚠️ **自评偏差**：同一模型评自己会系统性偏高。故 `JudgeRun` 单独存 `judgeModel`，并由 **J-13** 留出「judge 模型可单独指定」的口子。**这是已知局限，不藏。**

## 6. UI 草案

### 6.1 助手消息操作行

```
┌──────────────────────────────────────────────┐
│ 助手回答正文（Markdown，可含工具步骤折叠块）…  │
│                            ⧉    ♡    ♢    ⚡ │ ← 操作行，hover 才显形
└──────────────────────────────────────────────┘
                           复制  赞   踩   评测
```

| 状态 | 表现 |
|---|---|
| 默认 | 四枚 24px 图标，**次要色**，整行 hover 才显形（沿用复制按钮行为） |
| 赞/踩选中 | 选中项**主色**实心，另一项次要色；互斥，再点取消 |
| 评测中 | 评测图标**主色**+细旋转，点击禁用；其余三枚可用 |
| 已评测 | 评测图标**次要色实心**（再点＝重评），**无分数、无分数 tooltip** |
| 评测失败 | 图标转**危险色** 1.5s 后复原，理由只在设置页看 |

均带 `title`，不加文字标签、不加边框底色。

### 6.2 设置页「质量」分组（第 5 个，排在「账号」后）

```
┌ 设置 ─────────────────────────────────────────┐
│ 模型 │  质量                                   │
│ 外观 │  ─────────────────────────────────────  │
│ 记忆 │  近 30 天：已评测 12 条 · 平均 3.8 / 5   │ ← 大号主色数字
│ 账号 │  相关性 4.1 忠实度 3.5 完整性 3.9 表达 3.7│ ← 次要色细行
│ 质量 │  ─────────────────────────────────────  │
│      │  踩的样本（8）                           │
│      │  ┌────────────────────────────────────┐ │
│      │  │ 10-14 15:22 · 帮我看看 test.txt…    │ │
│      │  │ 3.2 分 · 忠实度最低  ▸ 查看          │ │
│      │  └────────────────────────────────────┘ │
│      │  （展开：理由 / 工具轨迹 / 指纹）         │
│      │  [ 评测最近未评测的 10 条 ] ← 次要按钮    │
└───────────────────────────────────────────────┘
```

层级：**汇总数字（主色）→ 维度细行（次要色）→ 样本列表（可展开）**。空态：「还没有评测记录。在任意回答下点「评测」即可开始。」只复用现有语义色，不新增色值。

## 7. 不做什么

| # | 排除项 | 说明 |
|---|---|---|
| 1 | **不做每条自动评分** | token 翻倍，用户已否决 |
| 2 | **不在对话界面显示分数** | 不干扰聊天 |
| 3 | **不做多模型投票 / 多次采样均值** | 成本 ×N，收益不确定 |
| 4 | **不做人工标注平台**（标注队列、多人复核、一致性 κ） | 单人本地工具，无此场景 |
| 5 | 不做 ragas 式 embeddings / 语义相似度指标 | 需向量模型，与 P3 冲突 |
| 6 | 不做服务端评测、不做 case 云同步 | 本次纯本地 |

## 8. 待确认问题（5 条，含我的推荐）

| # | 问题 | 推荐答案 |
|---|---|---|
| Q1 | 评测入口放哪？ | **操作行第 4 枚图标**（就近触发）；设置页批量作为 P1 |
| Q2 | 点赞/踩时是否立即建 case（多一次落盘）？ | **是**。否则踩的清单在用户评测前是空的，违背 G1 |
| Q3 | judge 用哪个模型？ | **P0 跟随会话模型，P1 允许单独指定**。自评偏差真实存在，但 P0 先跑通链路 |
| Q4 | 四维是否加权（如忠实度 ×2）？ | **不加权**。小样本下加权无统计意义，只多出一堆参数 |
| Q5 | 被中止/报错的回答能否评测？ | **不建 case**。低分会污染平均分 |

## 9. 给架构师的硬要求

1. **新增配置字段（judge 模型覆盖）必须同步加进 `normalizeConfig()` 白名单**，否则每次读盘静默丢失（`PROJECT-GUIDE.md` §8.2 的坑）。
2. `judge-cases.json` 走 `storage.ts` 的原子写 + `enqueue`；它与 `conversations.json` 同为 O(n) 写放大，不要在渲染层高频触发。
3. judge 请求**不带工具声明**（纯文本进、JSON 出），否则模型会想调工具；指纹哈希用内置 `node:crypto`（不算新依赖）取前 8 位。
